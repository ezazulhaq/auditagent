# AuditAgent v2.8.0 Release Notes

**Release Date:** November 14, 2026

AuditAgent 2.8.0 delivers **Phase 2: Database Performance Hardening & Storage Offloading**, optimizing relational persistence, search performance, and artifact storage during high-throughput repository security auditing. This release introduces a pre-computed, stored PostgreSQL `search_vector` column with GIN indexing for sub-millisecond lexical full-text search retrieval, implements native chunked batch finding upserts via `JdbcTemplate.batchUpdate` eliminating N+1 sequential database queries, deprecates relational JSON bloat in `reports.findings_json` in favor of normalized table queries, and integrates a reactive S3-compatible Supabase Storage REST client with resilient local filesystem fallback.

---

## 🚀 New Features & Enhancements

### 1. Stored Generated `search_vector` Column & GIN Indexing
* **PostgreSQL Schema Migration**:
  * Created `PostgresSchemaMigrationService.java` executing on application readiness to idempotently add `search_vector tsvector GENERATED ALWAYS AS (...) STORED` to `repository_memories`.
  * Created PostgreSQL GIN index `idx_repo_memories_search_vector` indexing pre-computed lexemes across finding title, summary, root cause, remediation pattern, and search text.
* **FTS Query Refactoring**:
  * Refactored `PostgresKnowledgeBaseService.java` to query `search_vector @@ plainto_tsquery('english', ?)` with ranking via `ts_rank_cd(search_vector, ...)`.
  * Replaces dynamic on-the-fly `to_tsvector` calculation in the `WHERE` clause, eliminating CPU-intensive sequential table scans as approved memory sets grow.
  * Preserved graceful metadata and text matching fallback for non-PostgreSQL engines (such as in-memory test databases).

### 2. Native PostgreSQL Batch Finding Upserts (`ScanDataService`)
* **N+1 Sequential Query Elimination**:
  * Replaced individual finding `SELECT` and `save()` loops with a single indexed pre-fetch query (`findByRepoPath`) reconciling existing findings in memory.
  * Preserves existing finding IDs, statuses (`FIXED`, `IGNORED`, `AWAITING_APPROVAL`), and proposed fixes across rescans, generating new UUIDs and `DETECTED` statuses only for newly identified findings.
* **Chunked Batch Persistence**:
  * Batch writes findings using Spring `JdbcTemplate.batchUpdate` with configurable batch chunking via `auditagent.database.batch-size` (default: `100`).
  * Employs native PostgreSQL `INSERT INTO vulnerabilities (...) ON CONFLICT (id) DO UPDATE SET ...`, with `MERGE INTO` compatibility for test environments.
  * Ingests 1,000+ scan findings in sub-second latency with zero N+1 database round trips.

### 3. Relational JSON Bloat Elimination
* **Decoupled Report Storage**:
  * Deprecated duplicated JSON serialization in `reports.findings_json`, storing `null` for new scans to prevent relational database table bloat and high WAL volume.
  * Updated `ScanDataService.mapToReport()` to lazily and transparently hydrate finding objects directly from the normalized `vulnerabilities` table, with backwards-compatible fallback for historical scans.

### 4. Reactive Supabase / S3 Storage Offloading Client
* **Cloud Object Storage Integration**:
  * Refactored `SupabaseStorageService.java` from a stubbed local implementation into a full reactive REST client using Spring `WebClient.Builder`.
  * Implemented `uploadBinaryArtifact`, `uploadTextArtifact`, `downloadArtifact`, and `downloadTextArtifact` targeting `/storage/v1/object/{bucket}/{path}`.
  * Enforces Bearer token authentication with Supabase service role key and configurable HTTP timeout (`auditagent.supabase.storage.timeout-seconds`, default: `15s`).
* **Resilient Local Filesystem Fallback**:
  * Automatically writes artifacts to local disk at `auditagent.supabase.storage.fallback-local-dir` (`.auditagent/storage`) returning `local://` URIs when remote storage is disabled (`auditagent.supabase.storage.enabled: false`), unconfigured, or unreachable (HTTP 5xx / timeouts).
